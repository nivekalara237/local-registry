Release notes come in a `CHANGELOG.md` file sent with each publication. The registry parses this file and turns its content into the `changes` list of `release.json`. It also flags the versions that contain security fixes.

This guide presents the two supported formats: the changelog generated by GoReleaser, and the [Keep a Changelog](https://keepachangelog.com) format, for notes written by hand.

Release notes are optional. Without a `CHANGELOG.md` file, `changes` stays an empty list.

## Which format to use?

| How you publish | Format to use | Written by |
| --- | --- | --- |
| You use GoReleaser with [Conventional Commits](https://www.conventionalcommits.org/) | The `dist/CHANGELOG.md` file generated by GoReleaser | GoReleaser, from the commit messages |
| You use another build tool, or want to write your own notes | Keep a Changelog | Your team, by hand |

Both formats can also live in the same file.

## With GoReleaser

GoReleaser generates a `dist/CHANGELOG.md` file at each release. Send it to the registry with the `--changelog-file dist/CHANGELOG.md` option of `localrectl publish`.

To get notes the registry can read:

1. **Use Conventional Commit messages.** For example: `feat(api): CSV export` or `fix(security): bump golang.org/x/net`.

2. **Keep the message prefixes.** In your `.goreleaser.yaml`, have the changelog read the messages from Git or GitHub, without removing the `feat:` and `fix:` prefixes:

   ```yaml
   changelog:
     use: github # or git
     sort: asc
     filters:
       exclude:
         - "^docs:"
         - "^test:"
         - "^chore:"
   ```

3. **Build your release with GoReleaser.** The commit messages kept become release notes:

   | Commit message | Generated note |
   | --- | --- |
   | `feat(api): CSV export` | `added`: CSV export |
   | `fix: projects beyond 500` | `fixed`: projects beyond 500 |
   | `fix(security): bump golang.org/x/net` | `security`: bump golang.org/x/net |
   | `perf: faster hashing` | `changed`: faster hashing |
   | `docs: typo` | No note |

The full mapping between prefixes and note kinds is in the [CHANGELOG.md reference](../reference/changelog-format.md).

> [!WARNING]
> If GoReleaser's `filters` rules or group titles (`groups`) remove the `feat:` and `fix:` prefixes from the messages, the registry can no longer tell their category. `changes` may then stay empty.

## By hand, with Keep a Changelog

You can write a `CHANGELOG.md` file yourself, in the Keep a Changelog format.

For a product whose versions are published one after the other, keep the notes in a single file, newest version first. Sort the changes under these standard headings:

- `Added`: new features.
- `Changed`: changes to existing features.
- `Deprecated`: features whose use is discouraged.
- `Removed`: features removed.
- `Fixed`: bug fixes.
- `Security`: security fixes.

Example:

```markdown
# Changelog

## [Unreleased]
### Added
- invoices table

## [1.1.0] - 2026-10-18
### Added
- orders table
### Security
- remove the default password

## [1.0.0] - 2026-09-01
### Added
- users and products tables
```

When the file holds several version sections, the registry extracts **only the one of the version being published**.

For example, publishing `v1.1.0` gives two notes:

- `added`: orders table
- `security`: remove the default password

The version heading may be written with or without the `v` prefix and brackets. These three forms all match `v1.1.0`:

- `## [1.1.0]`
- `## 1.1.0`
- `## v1.1.0`

The `Unreleased` section is never published.

> [!IMPORTANT]
> Add the section of the version **before you publish**. Without it, the version is published without notes. Once published, a version cannot be changed.

If your file has no version heading at all, the registry reads it whole. This suits small `CHANGELOG.md` files written for one publication each.

## Send the release notes

The `CHANGELOG.md` file must be sent with the files of the version:

- **With a directory of files:** put `CHANGELOG.md` in the directory published with `localrectl publish --root`.
- **With GoReleaser:** pass the `dist/CHANGELOG.md` file generated by GoReleaser with `--changelog-file dist/CHANGELOG.md`.

## Check the result

After publishing, read the version to check that the notes were understood:

```sh
curl -fsS https://registry.corp.example/bridge/releases/v1.1.0 \
  | jq '{securityUpdates, changes}'
```

Example answer:

```json
{
  "securityUpdates": true,
  "changes": [
    { "kind": "added", "description": "orders table" },
    { "kind": "security", "description": "remove the default password" }
  ]
}
```

`securityUpdates` is `true` when at least one note has the `security` kind. The flag also shows for each version in the product's `index.json`, so consumers can quickly spot the versions that contain security fixes.

## Limits

- Maximum size: 1 MiB.
- Accepted encoding: UTF-8.
- Windows line endings are accepted.
- The server checks the size and encoding of the file when it is uploaded. Otherwise it answers `422`.
- The release notes are parsed and extracted at publish time.
