title: Integrity
description: How the registry guarantees that every published file is exactly the file that was built, and how consumers verify it.
---

A registry is only useful if you can trust what you download. Local Registry checks every file before it publishes it, records its SHA-256, and hands consumers everything they need to verify it themselves. This page explains the checks, and what remains your responsibility.

## Three layers of checks

![The three layers of checks: on upload, on publish, on download](/img/three-layers-of-checks.svg)

**1. On upload.** Each `PUT` request may carry the SHA-256 computed by the publisher in the `X-Checksum-Sha256` header. The server also computes the SHA-256 of the file it receives and refuses the request on a mismatch (`422 sha256 mismatch`), before the file even enters staging.

This header is optional. To send it from your own clients, see the [Upload API](../reference/api/upload.md).

**2. On publish.** The server computes the SHA-256 of every staged file again, then checks the whole version against the checksums file:

- If you sent a checksums file (for example the one GoReleaser generates, matching `*checksums.txt`), every file must be listed in it with a matching SHA-256. A missing entry or any difference refuses the publication.
- If you sent no checksums file, the server writes `checksums.txt` itself, in the `<sha256>  <name>` format, from the files it just verified.

Example content of a checksums file (sums shortened):

```text
3f1c…  bridge_1.4.2_darwin_arm64.tar.gz
8a07…  bridge_1.4.2_linux_amd64.tar.gz
c9e2…  bridge_1.4.2_windows_amd64.zip
```

The checksums file does not list itself.

Either way, every published version has a checksums file consistent with all its files.

**3. On download.** The consumer can check the downloaded files by comparing their SHA-256 with the one given in `release.json`, or in the checksums file published with the version.

For example, to download an archive and check it against the checksums file:

```sh
curl -fsSLO https://registry.corp.example/bridge/artifacts/v1.4.2/files/bridge_1.4.2_linux_amd64.tar.gz

curl -fsSL https://registry.corp.example/bridge/artifacts/v1.4.2/files/bridge_1.4.2_checksums.txt \
  | sha256sum --check --ignore-missing
```

See [Consume releases](../guides/consume-releases.md) for complete client scripts.

## Files without a checksum line

Some files are left out of the checksums file on purpose:

- The product card (`registry.yaml`).
- The release notes (`CHANGELOG.md`).
- The metadata generated by GoReleaser (`metadata.json`, `artifacts.json`).
- The documents written by the server (`index.json`, `release.json`, etc.).
- Signature files (`*.sig`, `*.pem`, `*.sigstore.json`), which sign the checksums file itself.

Although they are left out of the checksums file, their SHA-256 is always recorded in the [audit log](../operations/audit-log.md) at publication.

## Signatures and SBOMs

When you publish signatures, certificates or SBOMs (with GoReleaser's `signs:` and `sboms:`), the server attaches each one to the file it covers, based on its name. It recognises in particular these suffixes: `<file>.sig`, `<file>.pem`, `<file>.sbom.json`, and their equivalents.

`release.json` then gives, for each artifact, the URLs of its SBOM (`sbom`), its signature (`signature`) and its certificate (`certificate`). The same applies to the checksums file.

> [!IMPORTANT]
> The server only attaches signatures and certificates to the files they cover: it does not check their cryptographic validity. Verifying signatures (with Cosign or GPG) against your trust policy is the consumer's job.
>
> Signing the checksums file is recommended: one signature then covers every file it lists, without signing each artifact.

## What the registry does not protect against

Be explicit about the limits:

| Threat | Covered? |
| --- | --- |
| A file corrupted in transit to the registry, or a wrong file uploaded | **Yes**, by the upload and publish checks |
| A published file changed through the API | **Yes**: published versions are immutable |
| Someone with write access to the storage directory changing a file | **No**: protect the directory and back it up. See [Storage and backup](../operations/storage-and-backup.md) |
| A file tampered with on the network to the consumer | **Only with HTTPS**, or with signature verification. See [Security](../operations/security.md) |
| A malicious build published with a valid token | **No**: protect the token, sign your releases |
